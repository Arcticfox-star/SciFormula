## 二、根因（已定位并复现）

`verify_formula` 的返回里含有一个**非法 JSON 字面量**：

```json
"noise_level": NaN,
```

`NaN` 不是合法 JSON（RFC 8259 不允许）。**Python 的 `json` 模块宽容地接受它**
（这是 Python 的扩展），所以我在本地怎么测都"正常"；而浏览器 / Node 的 `JSON.parse`
会直接抛错。AGH 客户端解析失败 → 这个请求永远不完成 → 60 秒后报 `Request timed out`。

**为什么只有 `verify_formula` 中招**：它是唯一会回显 `noise_level` 的工具。

**NaN 从哪来**：当天新加的「读磁盘数据文件」功能里，
`datasets.load_dataset` 给 `meta["noise"]` 写了 `float("nan")`（数据来自文件，
没有"我们加的噪声水平"这个概念）——于是这条新路径一上线就带着这个雷。

复现证据（本地用真实 MCP 协议问一遍，严格解析）：

```
响应里发现 NaN × 2
出现位置：..."small_scale_note": "真值最小的 5% 区间里有 31 点" },
         "noise_level": NaN, "thresholds": {...}
严格 JSON 校验（模拟 JSON.parse）→ ❌ 解析失败：非法常量 NaN
```

## 三、修复（两层 + 一条回归检查）

1. **堵源头**：`datasets.py` 的 `meta["noise"]` 从 `nan` 改为 `0.0`，
   并加 `noise_note` 显式说明"噪声水平未知"，而不是用 NaN 含糊表达。
2. **加一层全局净化**：`agh_tools._json_safe()` 递归地把返回里的
   `NaN` / `±Infinity` 转成 `null`，numpy 标量/数组转成原生类型，
   不可序列化对象兜底转字符串。**这道防线是通用的**——任何工具都不可能再吐出非法 JSON。
3. **回归检查**：`mcp_server.py --selftest` 新增第 6 步，
   对 `list_datasets` / `load_dataset` / `verify_formula` 的**原始字节**做严格 JSON 解析
   （`parse_constant` 抛错），把这类 bug 挡在提交之前。

修复后实测：三个工具的响应均「无 NaN/Infinity、严格 JSON 合法 ✔」。

## 五、人工分析（本段是人写的）

这场失败有三个层次的价值，都不是"跑通一场"能替代的：

1. **它抓出的是一个真实产品缺陷，而且是新功能自带的**。如果没有这次 AGH 闭环，
   这个 bug 会一直潜伏到评审现场——因为**本地测试被骗过去了**
   （Python 宽容解析掩盖了非法 JSON）。这正好回答"为什么必须真在 AGH 里跑"。
2. **模型的表现值得记下来**：三次重试失败后，它没有编造验证指标，
   而是明确写出「未能完成」并说明原因（"按不编造结果的原则"）。
   一条会**拒绝交付假结果**的智能体，比一条永远顺利的智能体更有说服力——
   这与第三个坑（负动能公式）和 `overfit` 拦截是同一条主张的三个侧面：
   **验证与诚实性优先于好看的数字。**
3. **它是提交要求的"失败类测试样例"的现成素材**，并且附带了完整的
   现象 → 根因 → 修复 → 回归验证链，可以直接放进报告。

> → `build_candidate_library` → `fit_sparse`）**全部成功返回真实数字**，
